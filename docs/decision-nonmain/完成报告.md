二、根因复核（用真实源码验证过，和用户遇到的现象一致）
--------------------------------------------------------------------------------
1) 走 OpenAI 兼容接口时，HTTP 错误先过 core 的通用分类器：
   core/.../model/ModelAccessErrors.kt 第 60 行：
       if (status != 400 && status != 403 && status != 404) return null
   Bamboo Relay 返回的是 **503**（响应体里才写着 "model_not_found:
   No available channel for model startlux-decision-27b-autothink"），
   503 不在这三个状态码里 → 分类器直接放弃。

2) 于是 OpenAiCompatModel 走到兜底分支：
   core/.../model/OpenAiCompatModel.kt 第 142 行：
       status in 500..599 -> ModelError.Server(status)
   → 结论：**503 + "model_not_found" 在 Mika 里被当成「服务端出错」，不是「找不到模型」。**

3) ModelSetupViewModel.probeModel() 把它记成：
       ProbeOutcome.Failed(message, modelReason = tr(model_reason_server), serverSide = true)

4) probe() 收尾：
       if (rejected.isNotEmpty() && rejected.all { it.serverSide }) return ListProbe.Blocked(...)
   因为列表里只有（或候选里排前面的都是）这种决策模型，rejected 全是 serverSide
   → 整家服务商判定为「不可用」→ Blocked → testAndSave() 直接 `return@launch`，
   **不保存任何东西**。用户在界面上看到的就是加不上这家。

5) 另一个更早的拦截点也在同一个探针里：
       firstServerError != null || i == 0 -> return ListProbe.Blocked(o.message)
   即：第一个候选 5xx 之后，如果下一个候选再失败，也是整家被拒。

一句话：决策模型在对话接口（/v1/chat/completions）上必然答不出工具调用，
而 Mika 的「测试并保存」正是用一次工具调用来判断这家的 Key 能不能用 ——
两种需求撞在一起，就成了「有一个决策模型就把整家挡在门外」。

三、这次改动做了什么
--------------------------------------------------------------------------------
核心原则：**把「这个模型的接口不对」和「这一家整体不可用」分开。**
名字里带 decision / startlux（不分大小写）的模型认定为「只适合非主模型用途」：
它试调用失败不再株连整家，服务商照常保存，只是不自动当主模型，
并在界面上说一句让用户到「用途」里选；反过来，它要是被选作主模型，会被明确拦下并给出原因。

改动文件（6 个）：

1. app/src/main/java/com/wangzan101/mika/ui/ModelSetupViewModel.kt（主改动）
   a. ModelSetupUi 增加字段 nonMainRoleNote：把决策模型设成主模型时的一句提醒
      （选好主模型、或再次保存服务商时清掉）。
   b. ListProbe.Done 增加 nonMain: List<String>：探针记下的「只适合非主模型用途」的模型名。
   c. probe()：
      - 新增分支：失败的模型若属于决策模型 → 记进 rejected + nonMain，继续试别的候选，
        不把它算成这家的问题；
      - 循环里新增：已经记到决策模型、且这次失败又是服务端错误/后续错误时，
        返回 Done（保存这家）而不是 Blocked；
      - 收尾的全 5xx 判定加上 && nonMain.isEmpty()：只有「没有一个模型能解释」时
        才判定整家不可用。
      - Key 不对（401）、地址错、网络错、超时这些不是服务端问题的失败，
        **判定逻辑一点没动**，原来会拒的照样拒。
   d. probeNote()：这家有决策模型时，在原提示后面补一句「服务商已保存，请在「用途」里
      把它们选作看图或轻量用途，不要当主模型」。
   e. pick() / pickManual()：role == Main 且模型是决策模型时，不改现有主模型，
      写入 nonMainRoleNote（pickManual 同时把它作为手填失败的提示），
      其它角色（看图 / 轻量）不受影响。
   f. companion object 增加 NON_MAIN_MODEL_TOKENS = listOf("decision", "startlux")，
      这就是「哪些模型算决策模型」的唯一出处，以后要加 rerank 之类改一行即可。

2. app/src/main/java/com/wangzan101/mika/ui/ModelSetupScreen.kt
   上手流程里把 nonMainRoleNote 显示在原 probeNote 下面（同色、同样一行小字）。

3. app/src/main/java/com/wangzan101/mika/ui/ModelsScreen.kt
   设置 › 模型的选择页里，选主模型（role == Main）时把这句提醒显示在页面顶部。

4-6. app/src/main/res/values/strings_setup.xml、values-zh/、values-b+zh+Hant/
     新增 3 条文案（英文 / 简体 / 繁体三份齐全，符合项目自带中英文资源的做法）：
     - model_reason_non_main：探针里「为什么它没通过」的短原因
       zh：它走的是决策接口，工具调用这一关测试注定过不了
     - model_probe_non_main：保存后补的那句（带 %1$s 模型名）
       zh：列表里这几个走的是决策接口而不是对话接口：%1$s。服务商已保存，
          请在「用途」里把它们选作看图或轻量用途，不要当主模型。
     - model_non_main_as_main：被拦下时的原因
       zh：「%1$s」走的是决策接口、不会调用工具，不能当主模型。
          请在「用途」里把它选作别的用途。

7. app/src/test/java/com/wangzan101/mika/ui/ModelSetupViewModelTest.kt（新增 2 个用例）
   - providerWithOnlyDecisionModelsIsSavedWithoutAMainModel
     只有决策模型的一家：503 也要存下服务商、不定主模型、提示里出现「用途」；
     选它当主模型被拦下且主模型不动；手填同名同样被拦；选作轻量用途能成功。
   - decisionModelIsRejectedAsMainButUsableForAnotherRole
     决策模型和通用模型在同一家：通用的当主模型；想把决策模型设成主模型被拦、
     提醒出现；选回通用模型后提醒消失；决策模型可以占「看图」这个用途。
   （项目 README「参与贡献 › 贡献代码」明确写了「改动请带单元测试」，这两条就是为此加的。）

八、已知限制（必须在 PR 里说清）
--------------------------------------------------------------------------------
1. 这个补丁解决的是「能配上、能选中」，**没有实现 /v1/decisions 调用**。
   Mika 实际用这个模型时仍然按对话接口发请求，调用会失败或结果不理想。
   要真正用起来，得在 core 的推理层再加一条走 /v1/decisions 的模型实现。
2. 判定方式是按模型名关键字（decision / startlux），属于启发式：
   名字里带这些词但不是决策模型的会被归到这一类（不会坏，只是不当主模型）；
   反过来，名字里不带这些词的决策模型享受不到这个优待。
   更严谨的做法是让服务商在模型列表接口里标明模型种类，那需要改 interfaces/ 那一层，
   不是最小补丁能做的。
3. 只在 Android Studio/命令行编译 + JVM 单元测试层面验证；真机行为需要上面的第 7 章验收。

补丁不管的事（真要让决策模型干活，下一步这么改）
   - 这次只动了「添加服务商 / 选用途」这一段 UI 逻辑，core 的推理层一个字没改；
   - 要让 Mika 真正按 /v1/decisions 用它，需要在 core/src/main/kotlin/.../core/model/
     下新增一个走决策接口的模型实现（请求体是 state + questions，回答是带概率的若干选项），
     再让「用途」能指定自己走哪类接口；
   - 更彻底的做法：ModelAccessErrors 和 /v1/models 返回的模型信息里带上模型种类
     （chat / decisions / embedding），这样就不用靠名字关键字猜了（这是给上游的第二个 PR 更合适的话题）。

九、给原作者的 PR 文案（可直接粘贴）
--------------------------------------------------------------------------------
标题：
    feat: 决策模型（StartLux 这类）不再拖累整家服务商，可留给看图/轻量用途

正文：
    问题
    决策模型（如 Bamboo Relay 上的 startlux-decision-27b-autothink）回答走自己的
    /v1/decisions 接口。把这类请求发到 /v1/chat/completions 上时，中转站会直接给 503。ModelAccessErrors 只认 400/403/404（ModelAccessErrors.kt:60），
    所以 503 落到 ModelError.Server，probeModel 记成 serverSide = true；
    probe() 收尾「试的全都是服务端出错」就判定整家不可用（Blocked），
    于是只要有（或候选里排前面的都是）这种模型，这家服务商完全存不下，
    连同一把 Key 上别的通用模型也用不了。

    改法
    把「这个模型的接口不对」和「这一家整体不可用」分开：名字里带 decision / startlux 的
    模型，试调用失败时记为「只适合非主模型用途」（ListProbe.Done.nonMain），
    不再株连整家；服务商照常保存、不自动设主模型，界面补一句让用户到「用途」里选；
    pick()/pickManual() 明确拦住把它们设成主模型，并给出原因。
    Key 不对、地址错、网络错、超时这些判定逻辑一字未动，原来会拒的照样拒。

    范围
    - ModelSetupViewModel.kt：probe() 的失败判定、probeNote()、pick()、pickManual()、
      ModelSetupUi.nonMainRoleNote、NON_MAIN_MODEL_TOKENS
    - ModelSetupScreen.kt / ModelsScreen.kt：显示被拦下时的那句提醒
    - strings_setup.xml（values / values-zh / values-b+zh+Hant）新增 3 条文案
    - ModelSetupViewModelTest.kt 新增 2 个用例

    已知限制
    只解决「能配上、能选中」，没有实现 /v1/decisions 调用：Mika 用它时仍按对话接口发请求。
    判定是按模型名关键字做的启发式。
